# HOUZZkit F1 在线更新与回滚实施方案

## 分期路线

| 交付期 | 范围 |
| --- | --- |
| 第一期 · SSD 管理 | 工作台新增「SSD 管理」，支持检测、初始化、迁移 Docker 数据和清理旧副本。迁移前沿用手动备份流程。见 [第一期 SSD 管理方案](ssd-management-phase-1.md) |
| 第二期 · 用户数据维护 | 通用备份、还原和恢复出厂。备份使用未加密归档 |
| 第三期 · 固件更新 | 先交付只读版本检查，再验证 SSD 上的 A/B 启动和回滚。在线安装需用户主动启用，且设备通过布局和存储预检 |

本文件保留第二期的数据维护设计和第三期的 OTA 实施方案。第一期工作台 `/firmware` 继续显示「敬请期待」。

Ubuntu 24.04 ARM64 和 Armbian Noble ARM64 都在 `main` 构建成功后发布正式版。设备只查询自己的发行版和板型。在线更新首版维持同发行版升级，换发行版和现有单槽设备的 A/B 迁移使用 USB 整包流程。

保留用户数据是 OTA 安装和回滚的验收条件。Docker 迁移入口归第一期「SSD 管理」，其余数据维护入口归第二期「数据与存储」。

## 1. 当前实现与启用条件

| 项目 | 已有行为 | OTA 实施要点 |
| --- | --- | --- |
| Rockchip 直刷整包 | `update.img` 包含 loader、U-Boot、参数表、boot、recovery、misc 和 rootfs | 保留现有 USB 刷机与救援路径。另行生成只包含允许在线写入内容的 OTA 包 |
| eMMC 布局 | GPT，只有一份 `boot` 和 `rootfs`。镜像大小会影响打包后的 rootfs 及 userdata 边界 | 新布局必须有两套成对的 boot/rootfs 及共享数据区。保留救援入口并验证分区空间 |
| 镜像识别 | `/etc/houzzkit-firmware.json` 已有发行版、版本、源提交、Actions 运行编号、BSP 内核版本及布局标识 | 当前布局标识是 `rockchip-gpt-single-rootfs-v1`。分区模板 SHA-256 标识构建输入。安装前还要核对设备上的实际 GPT、分区身份和启动槽 |
| 启动配置 | BSP 的 extboot 生成 extlinux 配置、内核、DTB 和可用的 initramfs | 在实板证明 U-Boot 能选槽、识别成套分区、有限重试并恢复。仅有设备树或 U-Boot 源码无法证明实板具备自动回退 |
| 管理工作台 | `htoold` 常驻并验证管理员会话，管理口使用 HTTPS | 前端查看状态和提交明确的动作。安装、重启、试启动确认和回滚由独立更新服务负责 |

现有实现见 [单槽分区模板](../houzzkit-f1-bsp-k6199/device/rockchip/.chips/rk3566_rk3568/parameter-ubuntu-fit.txt)、[BSP 引导镜像生成](../houzzkit-f1-bsp-k6199/device/rockchip/common/scripts/mk-kernel.sh) 和 [固件构建脚本](../.github/scripts/build-firmware.sh)。

## 2. 版本检查

1. 管理员进入 `/firmware`。页面读取本机镜像元数据，显示发行版、已安装版本和上次检查时间。点「检查更新」发起只读检查。
2. 后台访问配置好的 GitHub Releases 仓库，分页读取正式发布，排除草稿、PR 预发行版和另一发行版的产物。仓库级 Latest 只用于 GitHub 页面展示。应用从选中的具体版本读取下载链接，固件检查与下载都避开 `/releases/latest` 入口。当前命名为 `houzzkit-firmware-ubuntu-YYYY_MM_DD[_N]` 和 `houzzkit-firmware-armbian-YYYY_MM_DD[_N]`，编号按北京时间和发行版分别分配。
3. 签名发布索引尚未上线时，可以按已知正式版命名读取公开发布信息，显示为版本提示。对当前命名按日期及数字序号排序，无后缀视为 0。历史带发行版版本号的文件保留下载入口。无法从本机元数据可靠判断的旧命名，显示「当前版本无法比较」。出现无匹配发布、网络超时、限流或解析失败时，保留此前结果并标注上次成功检查时间。
4. 签名索引上线后，使用已验证的发行版版本序号比较。页面显示候选版本、发布说明、大小、适用布局、来源和是否需要重启。单槽设备可查看说明及 USB 整包下载。检查功能无需安装权限，无须下载镜像或修改本机启动状态。

建议接口为 `GET /api/v1/firmware` 和 `POST /api/v1/firmware/check`。两者要求管理员会话。手动检查复用同一进行中的请求，对发布 API 设置超时，在短时间内共享缓存。发布说明按纯文本显示或使用经过安全清理的渲染。

## 3. A/B 布局、更新框架及实板验证

第一期保留 eMMC 单槽系统，SSD 作为可选 Docker 数据盘。第三期优先验证在 eMMC 保留启动链、boot 槽及救援环境，并将 A/B 根分区放在 SSD 上。下文的 A/B 写槽和启动控制用于第三期验证。实际分区和空间预算待 F1 冷启动、双槽回退及拔掉 SSD 后仍可救援的实测确认。检测到数据 SSD 只用于提示有可用设备，开启 OTA 仍需用户主动配置并通过预检。

### 存储与启动控制

| 分区或区域 | 职责 |
| --- | --- |
| loader、U-Boot、recovery | 沿用经过验证的启动和 USB 救援路径。OTA 首版不写这些区域 |
| `boot_a`、`rootfs_a` | 验证布局中，槽 A 的内核、DTB 和 initramfs 位于 eMMC，配套根文件系统位于 SSD |
| `boot_b`、`rootfs_b` | 槽 B 使用相同的介质分工，容量与 A 对应 |
| 启动控制区 | 保存确认槽、试启动槽、槽可启动状态、剩余次数和有效性校验。U-Boot 必须能独立读取并在断电后恢复 |
| 持久维护状态区 | 位于 eMMC，独立于系统槽、用户数据清理范围和 SSD。保存未完成任务的恢复记录、当前有效的 Docker 存储位置和 OTA 防降级记录 |
| 共享数据区 | 保存本机账号状态、证书、绑定、启动报告和更新历史。Docker 数据按现有策略放 eMMC 或用户配置的 NVMe |

实施前分盘核算。eMMC 预留两套 boot、救援环境及控制和共享数据区。SSD 核算两套 rootfs、OTA 暂存和既有 Docker 数据所需的空间。按两种发行版较大的构建产物加余量确定槽尺寸，检查分区对齐约束。布局定稿后分配新的布局 ID，单槽 ID 继续用于原镜像。

安装端将实际挂载根分区、内核启动参数中的槽标识、启动控制记录和 GPT 交叉核对。按登记的 eMMC 与 SSD 设备身份以及各自 PARTUUID 定位写入目标，核查分区范围和容量，拒绝挂载中的槽、当前根分区和与配置不一致的介质。A/B 的同名文件系统可能有相同标签，应避免依赖文件系统标签识别槽位。

U-Boot 选择槽后，从对应的 boot 分区加载启动配置并向内核传递槽标识和 `root=PARTUUID=…`。initramfs 按该根分区标识挂载，`fstab` 的根挂载规则与槽选择保持一致。启动确认前，核对启动链传入的槽标识、实际根分区和候选记录。三者不一致时禁止确认和在线写槽，并按试启动失败处理。

验证步骤如下：

- 确认 F1 实际 U-Boot 配置、环境保存后端、读写位置和可恢复性。确认 boot/rootfs 槽切换不误触原厂 Recovery。
- 先在空白或已备份的实板上，用 USB 刷入 A/B 基础镜像。分别验证两个槽的冷启动、模块与实际内核一致、HDMI/串口和管理口可用。
- 故意让 B 的启动配置指向 A 的根分区，并验证反向场景。错误配对不得通过健康确认。原已确认槽应仍可启动。
- U-Boot 每次向候选槽交接前持久化一次尝试计数，耗尽后选择上一已确认且仍可启动的槽。建议最多试启动两次，具体计数与复位行为以实板结果为准。启动控制记录应具备可验证的冗余或恢复机制。读不到有效记录时应进入已证实的安全回退路径或 Recovery。
- 内核挂起需要可靠的复位来源才能消耗试启动次数。验证 BSP 硬件看门狗能覆盖从引导到 Linux 健康确认的必要窗口，并验证接管和关闭行为。用户态无法覆盖所有早期挂起阶段，验证失败时保持自动安装关闭。

可采用 RAUC 作为首选验证方案，由它处理签名 bundle 和槽位写入，保留 F1 的 U-Boot 与 Rockchip 启动集成。先验证当前 BSP 的内核、工具版本、存储和 bootloader 接口，再定包格式和具体组件。 [RAUC 槽位与引导集成](https://rauc.readthedocs.io/en/latest/integration.html) · [U-Boot Boot Count Limit](https://docs.u-boot.org/en/latest/api/bootcount.html)

### 单槽设备迁移

1. 先按下文的完整备份范围导出备份，保存到电脑或另外的存储设备。核对备份能读取、必需数据齐全以及 USB 救援路径可用。单槽设备没有网页备份入口时，先使用旧固件支持的导出方法或离线备份。
2. 通过维护窗口刷入支持 A/B 的整包，再按说明恢复数据。恢复后检查当前挂载槽、管理端入口和设备绑定。业务数据应记录备份位置及恢复工具。
3. 工作台用实际布局决定是否可在线安装。已有单槽镜像继续提供版本提示和下载。网页不提供重新分区操作。

## 4. 签名、安装、启动确认与回滚

### 发布信任

- 发布工作流同时输出 USB 整包和 OTA 包，二者共享版本标识，使用独立的文件名和用途说明。正式 OTA 包与索引由受保护的发布流程签名。PR 工作流只能产出预览构建。
- 已签名索引和清单至少包括模式版本、板型、架构、发行版、渠道、单调递增的版本序号、显示版本、源提交、适用布局、最低引导版本、所需共享数据模式版本、最小空间、资产长度和摘要。签名覆盖确定的原始字节或标准化格式。若有分卷，逐一校验长度、顺序和摘要，再校验完整包。OTA 包里的 boot 和 rootfs 来自同一次 BSP 构建。
- 优先使用成熟的签名索引和客户端。若采用 TUF，区分离线根信任、发布目标、快照和时间戳角色，按该协议实现轮换、撤销和过期检查。RAUC bundle 签名验证独立于 GitHub 资产的传输。确定密钥交接、密钥丢失和设备长期离线后的恢复流程。设备时间无法可信地验证元数据有效期时，显示原因并拒绝在线安装。 [The Update Framework 规范](https://theupdateframework.github.io/specification/latest/)
- 在相同板型、发行版和渠道内，一个版本序号只绑定一个签名 OTA 包摘要。发布后不得用同序号替换包。设备拒绝低于已确认最高序号的远端包。重试时只继续已登记且摘要一致的包，新安装应选择高于已确认下限的版本。
- 首次通过 USB 刷入 A/B 镜像时，从随镜像交付且可验证的发行版和版本记录初始化防降级下限，再开放在线安装。恢复出厂、任务历史丢失或本地手动回滚均不能降低该下限。下限记录缺失且无法从可信记录恢复时，暂停在线安装。手动回滚只选择本机已知可启动且兼容的上一槽。
- 完整上传并校验后才公开发布。对于安装端，可信发布索引只公布资产已齐全的版本。重复发布同一任务复用原版本，不替换已发布的签名资产。

### 更新任务与写入顺序

工作台只提交候选版本 ID 或本机上一槽的回滚请求。独立的特权服务从预配置的渠道解析资产和分区，接受固定操作，通过本机 IPC 验证调用者。接口不接收任意 URL、Shell、设备名或分区路径。更新任务使用单一互斥锁，同时只能下载、安装或回滚一项。

| 阶段 | 行为 | 中断后处理 |
| --- | --- | --- |
| 下载 | 校验清单、发行版、布局及空间。支持取消下载，限制暂存体积，保留上一次可读报告 | 可重试。仅在部分内容与签名清单及服务器响应吻合时续传 |
| 校验 | 校验长度、摘要、签名及支持范围。核对当前活动槽和分区容量 | 校验失败清理无效暂存，保留当前启动目标 |
| 写入 | 持久化任务 ID、原槽、目标槽与包摘要。先在启动控制区把目标槽标为不可启动并读回验证，再写非活动槽的 boot 和 rootfs。写入阶段关闭取消操作 | 保留原已确认槽。即使目标槽原先可回滚，也不得选择已被部分覆盖的槽。可在重新验证包和槽身份后重写 |
| 读回验证 | 将 boot 和 rootfs 同步到介质并分别读回，核对长度、摘要和配对信息。两者均通过才允许登记为候选槽 | 任何不一致都保持目标槽不可启动，并从原槽启动 |
| 试启动 | 先同步更新记录，再写入候选槽、原槽和剩余尝试次数。重新读取启动控制状态确认写入成功后再重启 | 明确记录待重启或已切换。启动时以实际槽和控制记录为准 |
| 启动确认 | 在有限时间内确认实际根分区是候选槽、共享状态挂载且可读写、本机 HTTPS 管理服务可用 | 确认超时由独立监督单元请求复位，看门狗兜底，U-Boot 在尝试次数耗尽后回退。没有网线、没有安装 NVMe 或 Zigbee 缺失不触发回退 |
| 手动回滚 | 显示上一槽版本和预计重启。确认槽完整且共享数据兼容后，将上一槽登记为试启动目标，保留当前已确认槽作为失败回退目标 | 上一槽通过相同的健康检查后才提交为已确认槽。失败时回到发起回滚前的当前槽，并保存结果及原因 |

任务恢复记录存放在持久维护状态区，包含任务 ID、状态、版本、包摘要、槽和结构化错误码。关键写入前后均保存可恢复状态。浏览器断开后任务继续。重新打开工作台后读取现有任务。旧槽根据实际启动槽及试启动记录区分已自动回滚、手动回滚和原因待确认。网页显示受限错误摘要，详细日志只记录诊断所需内容，避免写入凭证、带认证信息的 URL 或敏感配置。

### 试启动确认超时与复位

1. 候选槽早期启动时，独立的 systemd 监督单元依据启动控制记录和实际根分区识别试启动，用单调时钟计时。监督单元不依赖共享数据挂载、容器、网页或更新任务进程就绪。确认期限按两种固件的冷启动实测确定。
2. 健康检查通过后，确认端向启动控制区提交已确认槽，读回确认成功才允许解除试启动的复位保护。到期时监督单元重新读取控制记录，并与确认动作串行处理。若候选槽仍未确认，记录可取得的失败原因并请求重启。共享数据不可写时照常启动复位流程。
3. 硬件看门狗覆盖候选槽从引导到健康确认的必要窗口。如果 Linux 卡住、监督进程挂起或重启请求没有完成，看门狗应停止被续喂并触发复位。真机验证看门狗的喂狗责任、引导到 Linux 的交接和失效行为。复位后由 U-Boot 依据剩余次数重试或选择上一已确认槽。
4. 旧槽用实际槽位和启动控制记录重建结果。如果共享状态未能保存具体诊断，显示「试启动未确认，已回退，具体原因未知」。确认写入与超时复位之间的断电场景，以读回的启动控制记录为准恢复。

任一固件无法证明上述复位链路可用，或看门狗无法覆盖早期启动及监督失败时，应保持该固件的在线安装入口关闭。

### 共享数据与回滚兼容

系统槽和可变数据分别管理。OTA 只写非活动系统槽，回滚切换系统槽并继续使用当前用户数据。共享目录按分区或文件系统的稳定标识挂载，挂载失败时暂停安装或试启动确认。每种固件发布前维护一份持久化清单，列出逻辑数据项、实际路径和存储位置，以及需要备份的外部挂载。安装前核对候选包声明的挂载及权限规则。仍在旧系统槽内的用户数据，必须先迁到共享位置并验证可读后才能安装。候选槽试启动时再按清单检查实际挂载、权限和可读性，通过后才确认新槽。备份可用于迁移的恢复保障。发现无法核对的挂载时，列出受影响的数据并暂停升级。

| 数据 | 兼容策略 |
| --- | --- |
| 账号、用户文件和设备身份 | 保留 root 管理员密码记录、普通账号的 UID/GID、密码和组关系、家目录、SSH 授权密钥、首启锁、设备 TLS 证书与 SSH 主机密钥。按清单恢复凭据和用户账号记录，保留各槽自身的系统账号及其配置。共享状态异常时保持首启注册关闭。验收覆盖原密码登录工作台、普通账号 SSH 和 `su -` |
| Zigbee 绑定 | 当前带修订号的 JSON 能读取旧格式。旧程序采用严格解析，无法读取新版格式。实装 OTA 前确定兼容写法或回滚转换步骤，并验证绑定、更换及解绑各自可回退 |
| 启动报告、更新记录 | 网页保留最近三份完整启动报告。更新历史独立保留，并约定旧槽至少能读取当前任务的基础字段 |
| Compose 与容器数据 | 保留 Compose 文件、环境文件、用户安装的 1Panel 持久数据、命名卷、应用数据库和登记的宿主绑定目录。核对实际 Docker data-root 和 containerd 持久目录。业务文件应放入持久卷或登记目录 |
| 用户配置与额外安装内容 | 持久化清单列出受支持的配置文件和用户自有目录。同时列出两槽各自管理的系统包与配置。对手动安装的 APT 软件提供软件包清单或明确的重新安装步骤。无法自动保留的路径在升级确认前提示 |

首版 OTA 仅允许试启动和回滚期间新旧槽都能读写共享数据的版本组合。升级预检核对共享数据格式及 Docker 存储兼容性，试启动前限制可能改写共享数据格式的任务。需要不可逆迁移的版本走带备份的维护流程，先验证数据还原再开放。切回旧槽时保留升级后产生的用户数据。恢复旧时间点的数据由管理员从备份单独发起。

## 5. 第二期工作台「数据与存储」

备份、还原和恢复出厂入口仅管理员可见。任务显示操作范围、进度、预估停机和失败原因。还原与恢复出厂执行前重新验证管理员身份并确认影响范围。第一期 SSD 管理、第二期数据维护和后续 OTA 安装共用维护锁。试启动未确认时禁用会改动用户数据或存储位置的操作。恢复所需的任务状态写入持久维护状态区。开机先按该状态恢复未完成任务，再允许受影响的服务启动。浏览器断线后可重新打开查看任务进度。

### 备份数据与还原备份

1. 提供「完整用户数据」和「仅设备及应用配置」选项。备份预览列出包含的路径、预计大小和无法读取的外部卷或绑定目录。完整备份应覆盖家目录、账号与设备身份、Zigbee、Compose、应用数据和登记的存储路径。任一必需数据源缺盘、无法读取或未通过校验时，允许用户导出已有内容，但清单和界面必须标为「部分备份」并列出缺项。部分备份不能用于确认完整恢复能力。仅配置备份单独标记范围。需要重新拉取的镜像可以省略，自制且无法重新获取的镜像或容器内仍未持久化的数据单独提示并提供导出入口。
2. 对写入中的应用数据库使用应用支持的一致性备份方式，或在短暂停写后生成备份。备份清单记录版型、发行版、数据格式版本、时间、范围和校验值。两种备份均使用未加密的归档，经管理工作台导出到电脑或另行选择的存储。导出前提示归档未加密，并标明其中是否含密码散列、私钥或应用凭据。出厂重置或换盘前，备份应保存在操作目标之外。
3. 还原直接读取备份归档，先验证完整性、兼容性、所有目标挂载身份及剩余空间，再显示将覆盖的内容。部分备份可按选定项目还原，缺项保留现场数据。只还原清单许可的数据路径，拒绝归档越界路径及逃出目标目录的链接。
4. 同设备还原可恢复该设备原有身份。跨设备还原默认恢复用户业务数据，保留目标设备的网络身份和主机密钥。管理员在预览中确认账号、用户名冲突和绑定路径，避免复制设备身份或在目标机覆盖管理员访问权限。
5. 按预览确认范围后，先停写受影响的服务，并在各目标文件系统上暂存和校验数据。先确认账号和属主映射、目标挂载，再切换用户与应用数据，最后应用 Compose 和服务配置。跨盘切换逐项记录原位置、新位置及提交进度，保留旧数据直至所有目标校验通过。中断后先完成切换或恢复原数据，再启动受影响的服务。账号还原提交后让已有网页会话失效。

### 恢复出厂设置

默认清除设备管理的 eMMC 用户状态，包括已创建账号、家目录、应用配置和 eMMC 上的容器数据，并重建设备凭据，重启后重新进入 `/welcome`。保留当前已确认的固件、引导和救援分区、OTA 信任材料及防降级版本记录。保留已连接 SSD 的数据并解除应用自动挂载和启动关系。确需清除 SSD 时，用户须另外选中目标盘，确认型号、容量和唯一标识后再执行。

提交前显示删除清单并引导用户导出备份。先在清理范围之外的持久维护状态区记录重置任务，再停写、锁定 root 管理员密码并清理用户状态。断电后从维护状态区读取进度，继续完成清理并核对旧账号和凭据已失效。提交重置完成后才开放网页首启。A/B 两槽都应读取这一状态，避免切槽后重新使用已清除的账号或容器配置。

### 快速迁移 Docker 到 SSD

流程、存储切换、缺盘恢复、旧副本清理及 1Panel 验收见 [第一期 SSD 管理方案](ssd-management-phase-1.md#docker-数据迁移)。OTA 后续沿用第一期登记的活动数据位置。

| 25 · 恢复出厂设置 | 删除范围确认、默认保留 SSD、持久任务记录、清理后重新首启 | 清理期间断电，分别从两槽启动，确认旧凭据失效且防降级记录保留 |

每项完成后先审查代码、配置、输入输出和失败路径。开发机只做静态检查及必要的 ARM64 交叉编译。完整固件交给 GitHub Actions 构建。**Ubuntu 和 Armbian 都需要通过 F1 真机上的布局、启动链、断电恢复和共享数据验收。** 通过后才对该板型和布局开放安装。无论 OTA 是否启用，`main` 构建成功仍发布正式 USB 整包。
